## 2. 문서의 역할과 판정 기준

이 문서는 “제품이 무엇을 제공해야 하는가”와 “현재 코드에서 어디까지 제공하는가”를 함께 관리합니다. 폴더 구조, 라우트별 상세, 전체 테이블 목록, 작업 절차처럼 다른 문서가 책임지는 내용은 반복하지 않고 해당 문서로 연결합니다.

상태는 다음 기준으로 판정합니다.

| 상태 | 판정 기준 |
|---|---|
| **구현됨** | 화면(`app/**/page.tsx`)과 데이터 로직(`lib/*.ts` 또는 RPC)이 실제로 연결되어 있음 |
| **미완성** | 코드나 사용자 문구에서 일부만 동작하거나 의도적으로 미구현임이 직접 확인됨 |
| **확인 필요** | 테이블·컬럼·권한 정의 등 일부 근거는 있으나, 완성된 화면과 처리 흐름을 코드에서 확인하지 못함 |
| **운영 설정 필요** | 애플리케이션 코드는 존재하지만 외부 Provider, Supabase 스케줄러 또는 운영 DB 설정 없이는 완전히 동작하지 않음 |

판정 원칙:

- 테이블이나 컬럼이 존재한다는 이유만으로 **구현됨**으로 판단하지 않습니다.
- 저장소에서 검증할 수 없는 운영 환경 상태는 반드시 **확인 필요** 또는 **운영 설정 필요**로 둡니다.
- 문서와 코드가 다르면 코드를 기준으로 이 문서를 갱신합니다.
- “구현됨”은 코드 연결 여부를 뜻하며, 실제 운영 환경 QA 완료를 뜻하지 않습니다.
- 스키마에 있으나 앱에서 사용되지 않는 테이블 전체 목록과 검증 한계는 [향후 기능 후보](./DATABASE.md#5-향후-기능-후보-테이블)와 [용도·존속 여부가 불명확한 테이블](./DATABASE.md#6-코드-미사용이며-용도-또는-존속-여부가-불명확한-테이블)을 기준으로 합니다.

## 3. 프로젝트 목표

센터(필라테스샵·헬스장·발레학원 등 운동시설)를 위한 통합 예약·회원 관리 앱을 제공하는 것이 목표입니다. 하나의 코드베이스에서 다음 세 사용자 유형을 지원합니다.

- 회원은 센터를 찾고 수업을 예약하며 수강권과 상품을 구매합니다.
- 센터 매니저와 강사는 수업, 회원, 예약, 매출과 운영 설정을 관리합니다.
- 플랫폼 운영자는 입점 센터와 서비스 노출 정보를 관리합니다.

한 계정은 여러 회원 프로필과 여러 센터 소속을 동시에 가질 수 있습니다. 제품 UX는 회원이 `예약 → 결제 → 수강` 흐름을 가능한 적은 판단과 클릭으로 이어갈 수 있도록 하는 것을 지향합니다.

| 알림 | 부분 구현 / 운영 설정 필요 | Realtime 알림함은 구현됨. 외부 푸시·알림톡과 정기 스케줄러는 미완성 또는 설정 필요 |

| 스키마 확장 기능 | 확인 필요 | 강사 배정, 락커, 양도, 계약, 커뮤니티 등은 스키마 흔적만 있고 완성 흐름을 확인하지 못한 항목이 있음 |

## 5. 구현된 기능

### 5-1. 인증과 계정

- 이메일/비밀번호 회원가입과 로그인 (`app/login/page.tsx`, Supabase Auth)
- 계정(`accounts`) 하나에 여러 회원 프로필(`profiles`)과 여러 매니저-센터 소속(`manager_centers`) 연결
- 회원 역할과 매니저 역할의 공존 및 모드 전환
- 매니저 가입 시 승인 대기 상태(`pending`)의 센터 자동 생성
- 사업자등록증을 Supabase Storage 비공개 버킷 `business-licenses`에 업로드 (`lib/storage.ts`)
  - `app/login/page.tsx`에 실제 업로드가 필요하다는 과거 TODO 주석이 남아 있지만 업로드 자체는 구현되어 있습니다.
- 카카오·애플 소셜 로그인 UI와 Supabase OAuth 호출
  - 실제 사용에는 Provider 설정이 필요합니다. 설정 방법은 [AUTH_SETUP.md](../AUTH_SETUP.md)를 참고합니다.

### 5-2. 예약

- 달력 기반 월간 수업 조회
- 센터 휴무일(`center_holidays`) 조회와 표시
- 수강권을 사용한 예약, 예약 취소, 대기자 등록
- 출석과 노쇼 처리
- 취소 트랜잭션 안에서 대기 1순위를 `confirmed`로 바꾸는 자동 승격 (`cancel_reservation`, `fix_waitlist.sql`)
- 대표 프로필이 구매한 수강권을 같은 계정의 다른 프로필이 사용하는 프로필 간 공유 (`add_shared_passes.sql`)
- 수강권별 요일·시간·수업명 예약 제한 (`membership_schedule_rules`)
- 수강권 발급 시 요일반을 자동 예약하는 `auto_book_membership()`
- 하루 한 번 자동예약 제한 (`fix_auto_book_oneperday.sql`)
- 정원 등의 이유로 배치되지 않은 수강권을 매니저가 “다시 배치”하는 재시도 UI (`app/manager/classes/page.tsx`, `retryAutoBook()`)
- 다중예약 허용 수강권 (`allow_multi_booking`)
- 예약·취소 마감과 마감 후 취소 시 횟수 차감 옵션 (`center_settings.deduct_on_late_cancel`)
- 사용 가능한 수강권이 없을 때 해당 수업에 맞는 구매 가능 상품 안내
- 예약에서 센터 상품 구매와 주문 화면으로 이동한 뒤 기존 예약 화면으로 돌아오는 흐름

국경일 표시는 별도 API가 아니라 `app/reservation/page.tsx`에 `2026-07-17` 제헌절 한 건만 하드코딩되어 있습니다. 이는 구현된 달력 기능의 현재 제한이며 후속 작업은 [TODO.md](./TODO.md)를 참고합니다.

### 5-6. 후기, 공지, 알림과 문의

- 별점·사진 후기 작성

- `notifications` 테이블과 Supabase Realtime을 이용한 실시간 팝업 및 누적 알림함

### 5-7. 역할과 권한

- 센터별 오너·매니저·강사 및 커스텀 역할 생성
- 권한 카탈로그(`permissions`) 기반 역할별 권한 부여 (`role_permissions`)
- 개인별 허용·차단 예외 (`account_center_permissions`)
- DB 함수 `has_permission(center_id, permission_key)`를 통한 서버 측 권한 강제

단, 프론트엔드는 대부분의 관리 기능에서 세부 권한에 따라 메뉴나 버튼을 숨기지 않습니다. 권한이 없는 작업은 조작 후 RLS/RPC에서 거부됩니다. 라우트별 클라이언트 가드와 실제 노출 상태는 [센터 매니저 라우트](./ROUTES.md#5-센터-매니저-라우트)와 [플랫폼 운영자 라우트](./ROUTES.md#6-플랫폼-운영자-라우트)를 기준으로 합니다.

## 6. 미완성 및 확인 필요 기능

### 6-1. 미완성

| 기능 | 현재 상태 | 코드 근거 |
|---|---|---|
| 실제 결제(PG) | 주문서만 `pending`으로 생성하며 카드·간편결제를 실제 처리하지 않음. 센터가 수동 확인·발급 | `app/checkout/page.tsx`, `lib/orders.ts` |
| 네이버 소셜 로그인 | 버튼은 있지만 클릭 시 미설정 안내만 표시 | `app/login/page.tsx`, [AUTH_SETUP.md](../AUTH_SETUP.md) |
| 푸시·알림톡 발송 | 알림 설정은 기기 로컬 저장이며 SMS·FCM·알림톡 발송기 연동 없음 | `app/settings/notifications/page.tsx` |
| 미발급 주문 취소 | 앱에서 직접 취소할 수 없고 센터 문의로 안내 | `app/purchases/page.tsx` |
| 환불 정책 설정 | 발급 후 24시간 이내·미사용 조건이 코드에 고정되어 있어 운영 정책을 설정으로 변경할 수 없음 | `lib/mypage.ts`, `lib/orders.ts` |
| 세부 권한 기반 관리 UI | DB 권한은 강제되지만 권한 없는 메뉴·버튼을 사전에 숨기거나 비활성화하지 않음 | `lib/roles.ts`, `/manager/*` |
| 담당회원·상담고객 화면 | 회원 화면에 준비 중 안내가 있으며 완성된 관리 흐름 없음 | `app/manager/members/page.tsx` |

### 6-2. 운영 설정 필요

| 기능 | 필요한 확인 또는 설정 |
|---|---|
| 카카오·애플 로그인 | Supabase Auth Provider와 Redirect URL 설정 |
| 예약 리마인드·수강권 만료 알림 | `notify_upcoming_reservations()`, `notify_expiring_passes()`를 호출할 pg_cron 등 정기 스케줄러 |
| Realtime 알림·문의 | 운영 Supabase의 Realtime publication과 관련 RLS 적용 상태 |
| SQL 마이그레이션 | 저장소의 SQL 파일이 운영 Supabase에 실제로 적용되었는지 별도 확인. 저장소만으로 적용 상태를 단정하지 않음 |

환경 설정 안내에서 참조하는 `.env.local.example`은 현재 저장소에 없습니다. 이는 제품 기능이 아니라 개발환경 문서·파일의 미완성 항목이며 [TODO.md](./TODO.md)에서 관리합니다.

| 수강권 양도 | `membership_transfers`, `payments.sale_type = transfer_fee` | 실제 재배정과 양도 이력 기록 코드 |
| 락커 배정 | `lockers`, `locker_assignments`, `center_settings.use_locker` | 락커 CRUD와 회원 배정 UI |
| 포인트 통합 | 매출은 `point_transactions`, 후기는 `point_accounts` 사용 | 두 잔액 체계가 하나로 동기화되는지 여부 |
| 커뮤니티·대회정보 | `community_posts`, `community_comments`, `competitions` | 실제 화면과 데이터 호출 |
| 전자계약서 | `contract_templates`, `terms`, `contracts` 및 관련 권한 | 작성·서명 화면과 처리 흐름 |
| 스태프 급여·근무일정 | `staff_salaries`, `staff_schedules`, `schedule_memos` 및 관련 권한 | 실제 운영 화면 |
| 팝업공지·메시지 발송 기록 | `popup_notices`, `messages` | 노출·발송 구현 |

전체 미사용 스키마 목록과 테이블별 근거는 [DATABASE 5절](./DATABASE.md#5-향후-기능-후보-테이블)과 [DATABASE 6절](./DATABASE.md#6-코드-미사용이며-용도-또는-존속-여부가-불명확한-테이블)을 참고합니다.

## 7. 플랫폼 운영자 기능

플랫폼 운영자는 `accounts.is_platform_admin = true`인 계정입니다. 일반 가입으로 이 권한을 얻을 수 없으며 DB에서 별도로 부여해야 합니다 (`add_platform_admin.sql`).

구현된 기능:

- 운영자 설정 허브
- 가입 대기 센터 조회
- 센터 사업자 정보 확인
- 센터 승인, 반려, 대기 상태 복원
- 서비스 종목(카테고리) 추가·삭제
- 홈 배너 추가·삭제·노출 순서 관리

`/admin/categories`와 `/admin/banners`는 클라이언트 가드가 없지만 쓰기는 RLS에서 플랫폼 운영자로 제한됩니다. 플랫폼 운영자 라우트별 접근 통제 상세는 [ROUTES 6절](./ROUTES.md#6-플랫폼-운영자-라우트)을 참고합니다.

## 8. 센터 매니저 기능

센터 운영 권한은 `manager_centers` 소속과 센터별 역할·권한으로 구성됩니다. 오너는 전권을 가지며 매니저·강사·커스텀 역할은 권한 카탈로그로 세분화됩니다.

구현된 기능:

- 대시보드의 센터 선택, 오늘 수업과 예약 현황
- 수업·반복수업·스케줄 복사·룸 관리
- 출석·노쇼·보강 예약과 미배치 자동예약 재시도
- 회원 검색, 등급, 상태, 메모, 주소, CSV 내보내기
- 진도 카테고리와 회원별 진도 기록
- 수강권 상품과 예약 조건 관리
- 굿즈·대여 상품 관리
- 결제, 지출, 포인트와 매출 리포트
- 회원 주문 확인과 발급
- 공지 작성, 후기 답변, 1:1 문의 응대
- 센터 정보, 운영 설정, 휴무일 관리
- 스태프 초대·역할 변경·삭제
- 역할별 권한과 개인별 권한 예외 설정

현재 제한:

- 세부 권한은 서버에서 강제되지만 대부분의 화면 UI에는 선반영되지 않습니다.
- 일부 매니저 페이지는 `fetchMyCenters()` 클라이언트 체크 없이 RLS에만 의존합니다.
- 담당회원·상담고객 기능은 준비 중입니다.

정확한 매니저 라우트 목록과 가드 여부는 [ROUTES 5절](./ROUTES.md#5-센터-매니저-라우트)을 기준으로 합니다.

## 9. 회원 기능

구현된 기능:

- 홈의 센터 조회, 카테고리 필터와 검색
- 센터 소개, 주소, 연락처, 수업 목록과 후기 조회
- 여러 수강 프로필 생성·편집·삭제
- 월간 예약 캘린더, 수업 예약·취소와 내 예약 목록
- 장바구니, 주문서 생성과 구매 내역 조회
- 수강권 현황과 예약 이력 확인
- 센터 상세에서 포인트 잔액 확인
- 결제 화면에서 포인트 사용
- 별점·사진 후기 작성
- 공지사항과 알림함 확인
- 센터 1:1 문의
- 기기별 알림 설정과 테마 설정

포인트 잔액은 마이페이지(`/mypage`)가 아니라 센터 상세(`/center/[id]`)에서 표시됩니다. 이전 문서에 마이페이지가 포인트를 표시한다고 적힌 내용은 코드 재검증 결과 사실이 아니었습니다.

현재 제한:

- 결제 버튼은 실제 PG 결제가 아니라 주문 접수입니다.
- 미발급 주문은 앱에서 직접 취소할 수 없습니다.
- 외부 푸시·알림톡 설정은 실제 발송으로 이어지지 않습니다.

회원 라우트와 로그인 처리 방식은 [공개·공용 라우트](./ROUTES.md#3-공개-및-공용-라우트)와 [회원 라우트](./ROUTES.md#4-회원-라우트)를 참고합니다.

## 10. 핵심 비즈니스 규칙

### 10-1. 계정과 권한

- 로그인 단위인 `accounts`와 수강 주체인 `profiles`를 분리합니다.
- 한 계정은 여러 프로필과 여러 센터 소속을 가질 수 있습니다.
- 플랫폼 운영자와 센터 운영자는 서로 다른 권한 체계입니다.
- 클라이언트 UI가 아니라 Supabase RLS와 RPC가 최종 접근 통제 계층입니다.

### 10-2. 예약

- 같은 프로필은 같은 수업을 중복 예약할 수 없습니다.
  - 활성 상태 `confirmed`, `waitlisted`를 대상으로 하는 유니크 인덱스로 제한합니다.
- 수강권 잔여 횟수는 DB 제약으로 음수가 될 수 없습니다 (`memberships_remaining_not_negative`).
- 예약 가능한 수강권은 센터, 상품, 상태, 유효기간, 잔여횟수와 수업별 허용 상품을 기준으로 판정합니다.
- 요일·시간·수업명 제한이 있는 수강권은 `membership_schedule_rules`를 따릅니다.
- 정원이 차면 대기 등록하고, 취소가 발생하면 대기 1순위를 즉시 승격합니다.
- 예약·취소·대기 마감, 당일 예약, 폐강과 마감 후 차감 정책은 센터 설정을 따릅니다.
- 다중예약 허용 여부와 자동예약의 하루 한 번 제한을 수강권 규칙에 반영합니다.

### 10-3. 수강권

- 수강권은 횟수권(`count`)과 기간권(`period`)으로 구분합니다.
- 기간권은 자동연장(`auto_renew`) 속성을 가질 수 있습니다.
- 같은 계정의 프로필은 공유 방식으로 수강권을 사용할 수 있습니다.
- 발급된 요일반 수강권은 조건에 맞는 수업을 자동 예약하며, 실패한 잔여분은 매니저가 재시도할 수 있습니다.
- 정지·환불 상태는 기존 DB 상태값과 제약을 따라야 합니다.
- 양도는 스키마 흔적만 확인되므로 구현된 규칙으로 간주하지 않습니다.

### 10-4. 주문, 결제와 매출

- 회원 결제 화면은 현재 실제 결제가 아니라 `pending` 주문을 생성합니다.
- 수강권 발급은 매니저가 주문을 확인하고 처리한 이후 발생합니다.
- 결제 원장은 카드·현금·계좌이체·포인트 분할 금액의 합계를 관리합니다.
- 미수금과 위약금은 별도 금액으로 관리합니다.
- 매출 구분은 신규·재결제·체험·업그레이드·환불·미수금결제·양도수수료를 포함합니다.
- 매출 종류는 수강권·수업·기타로 구분합니다.
- 결제 상태는 `pending`·`paid`·`refunded`·`failed`를 사용합니다.
- 가상계좌 필드는 스키마에 있지만 PG가 연결되지 않았으므로 실제 자동 입금 처리는 구현된 것으로 보지 않습니다.

핵심 테이블 컬럼, 관계, RLS와 SQL 원본 위치는 [DATABASE.md](./DATABASE.md)를 참고합니다.

## 11. UX 요구사항

- 회원의 핵심 흐름은 `수업 선택 → 사용 가능한 수강권 확인 → 필요 시 상품 선택과 주문 → 원래 예약으로 복귀`가 끊기지 않아야 합니다.
- 사용 가능한 수강권이 여러 개면 기본 선택을 제공하되 회원이 다른 수강권을 직접 선택할 수 있어야 합니다.
- 구매 가능한 상품 필터는 편의 기능이며 실제 예약 가능 조건과 혼동되지 않도록 안내해야 합니다.
- 주문 접수와 실제 결제·수강권 발급을 같은 의미로 표현하지 않습니다.
- 미구현 기능은 성공한 것처럼 가장하지 않고 현재 제한과 다음 행동을 명확히 안내합니다.
- 권한이 없는 사용자는 가능한 한 조작 전에 메뉴나 버튼 상태로 알 수 있어야 합니다. 현재 서버 거부에만 의존하는 화면은 개선 대상입니다.
- 비로그인, 권한 없음, 빈 목록, 로딩, 요청 실패 상태에서 사용자가 다음 행동을 이해할 수 있어야 합니다.
- 사용자 문구는 반말이 아닌 일관된 존댓말과 기존의 “~해요” 톤을 유지합니다.
- 화면 간 이동에서는 선택한 날짜, 센터, 수업과 이전 맥락을 가능한 한 보존합니다.
- 빠른 수업 전환이나 중복 요청에서도 이전 응답이 현재 화면 상태를 덮어쓰지 않아야 합니다.

## 13. AI 작업 시 문서 갱신 규칙

AI 도구가 기능을 추가하거나 변경할 때 이 문서를 다음과 같이 갱신합니다.

1. 작업 전 관련 요구사항과 현재 상태를 확인합니다.
2. 실제 화면과 데이터 로직을 모두 확인한 경우에만 **구현됨**으로 바꿉니다.
3. SQL만 추가했거나 UI만 존재하면 **구현됨**으로 올리지 않습니다.
4. 운영 Supabase 적용 여부, OAuth Provider, 스케줄러 등 저장소 밖 상태는 추측하지 않고 **운영 설정 필요** 또는 **확인 필요**로 기록합니다.
5. 부분 구현은 동작하는 범위와 빠진 범위를 함께 적습니다.
6. 기존 경고가 해결되었으면 근거 파일과 검증 결과를 확인한 뒤 상태를 변경합니다. 근거 없이 경고를 삭제하지 않습니다.
7. 테이블·컬럼·RLS·SQL 상세는 [DATABASE.md](./DATABASE.md), 라우트와 가드는 [ROUTES.md](./ROUTES.md), 우선순위와 기술 부채는 [TODO.md](./TODO.md)에 기록하고 여기에는 요구사항 수준의 요약과 링크만 남깁니다.
8. 완료된 변경은 [CHANGELOG.md](./CHANGELOG.md)에 날짜와 함께 기록합니다.
9. 새 요구사항은 플랫폼 운영자, 센터 매니저, 회원 중 영향을 받는 사용자를 명시합니다.
10. 예약·결제·권한처럼 상태 전이와 접근 통제가 있는 변경은 핵심 비즈니스 규칙과 UX 요구사항도 함께 재검토합니다.

구체적인 코드 변경 절차와 검증 명령은 [AI_PLAYBOOK.md](./AI_PLAYBOOK.md), 코딩·Git·DB 변경 규칙은 [DEVELOPMENT_RULES.md](./DEVELOPMENT_RULES.md)를 따릅니다.
