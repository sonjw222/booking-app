# 회원가입 휴대폰 번호 인증 — 조사 문서 (Track 6, 2026-08-03)

AUTH-001(#40) 후속 검토용 조사 문서. **구현·계약·외부 서비스 신청은 하지 않았음** — 아래는
모두 조사/검토 내용이며, P3 Deferred 상태를 유지한다.

## 1. Supabase Phone Auth 사용 가능 여부

Supabase Auth는 `signInWithOtp({ phone })` / `verifyOtp({ phone, token, type: 'sms' })` 형태의
SMS OTP 인증을 공식 지원한다(이메일 인증과 별개의 provider). 다만 Supabase 자체는 SMS를
발송하지 않고 **반드시 외부 SMS 사업자(Twilio, MessageBird, Vonage, 또는 국내는 커스텀
SMS Provider 연동)를 Supabase 대시보드에 등록**해야 동작한다 — 이메일 인증과 달리 "그냥
켜면 되는" 기능이 아니다.

## 2. 국내 SMS 발송 비용과 제한

- Supabase가 공식 지원하는 해외 사업자(Twilio 등)는 국내(+82) 번호 발송 시 국제 SMS
  요금이 적용되어 국내 전용 서비스(NHN Toast, 알리고, 솔라피 등)보다 건당 비용이 높고,
  발신자 사전등록(080/발신번호 사전등록제) 요건이 국내 사업자 기준과 다를 수 있음.
- 국내 서비스(카카오 알림톡/SMS 대행사)를 쓰려면 Supabase의 "Custom SMS Provider"(webhook
  기반)로 직접 연동해야 함 — Supabase 대시보드에서 바로 선택 가능한 옵션이 아니라 별도
  개발 필요.
- 이 프로젝트는 이미 `notification_rules`/`messages`/`notification_logs` 스키마가 존재하지만
  실제 SMS 발송 백엔드가 전혀 없음(E-3 감사에서 확인됨, `docs/TODO.md` 참고) — 휴대폰 인증을
  위한 SMS 발송과, 예약 알림용 SMS 발송(향후 과제)이 결국 같은 발송 인프라를 공유하게 될
  가능성이 높음 — 두 요구사항을 함께 검토해 사업자를 선정하는 편이 중복 계약을 피할 수 있음.

## 3. 기존 email/password 계정과 phone 연결 방식

현재 `accounts` 테이블은 `auth_id`(Supabase Auth user id) 1:1 연결에 `phone` 컬럼이 이미
존재하지만 **인증되지 않은 자유 입력 텍스트**로 저장된다(로그인/가입 화면에서 검증 없이
그대로 insert). Supabase Auth의 phone 인증을 실제로 쓰려면 두 가지 경로 중 선택 필요:
- (A) Auth user 자체에 phone을 등록(`auth.users.phone`) — Supabase Auth가 인증 상태를 직접
  관리, 이메일과 별개의 로그인 수단이 됨.
- (B) 지금처럼 `accounts.phone`은 애플리케이션 레벨 텍스트로 두고, 가입 시점에만 OTP로
  1회성 검증 후 저장(Auth user의 phone 필드는 안 씀) — 기존 이메일 기반 로그인 구조를
  바꾸지 않아도 되는 더 작은 변경.

## 4. 전화번호 중복 정책

`accounts.phone`은 이미 `unique` 제약이 있음(schema.sql 확인) — 한 번호로 여러 계정 생성은
현재도 DB 레벨에서 막혀 있음. 인증을 추가해도 이 제약은 그대로 유지 가능. 단, "번호는
유일하지만 검증되지 않았다"에서 "번호가 유일하고 검증됐다"로 바뀌는 것이므로, 이미 가입한
기존 회원들의 번호가 실제로 그 사람 소유인지는 소급 검증되지 않는다는 점은 명확히 인지 필요.

## 5. 번호 변경 및 재인증

번호 변경 시에도 재인증(새 번호로 OTP 재발송·검증)이 필요 — 현재 마이페이지에 번호 변경
UI가 있는지 별도 확인 필요(이번 조사에서는 미확인, 후속 조사 항목).

## 6. OTP 만료·재전송 제한

Supabase Auth의 OTP는 기본 만료 시간과 재전송 쿨다운을 대시보드에서 설정 가능(기본값은
프로젝트 생성 시점 Supabase 버전에 따라 다를 수 있어 실제 프로젝트 설정 확인 필요 — 이번
조사에서는 문서 조사만 진행, 실제 프로젝트 대시보드는 확인하지 않음).

## 7. Abuse/Rate Limit

무료/저가 SMS 사업자를 남용한 대량 OTP 요청(SMS bombing)은 실제 발생하는 공격 패턴 —
Supabase Auth 자체의 rate limit 외에 애플리케이션 레벨에서도 IP/계정당 요청 빈도 제한이
필요. 비용이 직접 청구되는 SMS 특성상 이메일 인증보다 abuse 방지 설계의 우선순위가 높음.

## 8. 기존 회원 마이그레이션

인증을 도입해도 **기존 회원을 강제로 재인증시킬 필요는 없음**(신규 가입자부터 적용,
`accounts.phone`이 이미 있는 기존 회원은 그대로 두는 점진적 도입이 일반적) — 다만 "인증된
번호"와 "미인증 번호"를 구분할 플래그(`accounts.phone_verified boolean` 등)가 추가로
필요해짐.

## 9. 개인정보처리방침/동의 영향

전화번호는 이미 수집 중인 개인정보라 신규 항목 추가는 아니지만, "SMS 발송을 위해 제3자
(SMS 사업자)에게 번호를 위탁 처리한다"는 문구가 개인정보처리방침에 없다면 추가·재동의가
필요할 수 있음 — 법무 검토 필요 항목으로 분류(제품/법무 결정 필요, 코드 조사 범위 밖).

## 10. 사업자/발신번호 등록 필요 여부

국내 SMS 발송은 통신사 심의를 거친 발신번호 등록이 사실상 필수(불법 스팸 방지 규제) —
사업자등록증 기반 발신번호 사전등록 절차가 필요하며, 이는 실제 SMS 사업자 계약 시점에
결정되는 외부 행정 절차로 코드 작업과 무관.

## 종합 결론

전화번호 인증 도입은 **(1) SMS 사업자 선정·계약(발신번호 등록 포함), (2) Supabase Auth
phone 연동 방식(A/B) 결정, (3) 개인정보처리방침 반영, (4) abuse 방지 설계**가 모두 제품/법무
결정을 필요로 하는 항목이라 이번 배치 범위를 넘어선다. AUTH-001(#40)은 계속 P3 Deferred로
유지하고, 예약 알림용 SMS 발송 인프라 도입 시점과 함께 재검토하는 것을 권장한다(같은 발송
인프라를 공유할 가능성이 높으므로).
