## 2. 전체 표준 흐름

```text
1. NotebookLM
   문서 기반 사실·정책·배경 정리
          │
          ▼
2. ChatGPT
   기능 기획·요구사항·검증 기준 정리
          │
          ▼
3. Claude Code 또는 Codex
   저장소 재검증·구현·수정·1차 문서 반영
          │
          ▼
4. 로컬 테스트
   수동 시나리오·build·diff 검수
          │
          ▼
5. GitHub
   commit·push·리뷰·원격 기준선
          │
          ▼
6. Vercel
   Preview/Production build·배포·배포 확인
          │
          ▼
7. Graphify 및 문서 갱신
   최종 구조 시각화·배포 결과·남은 작업 기록
```

각 화살표는 자동 진행을 뜻하지 않습니다. 검수 기준을 통과하고, push·배포·파괴적 DB 변경처럼 별도 권한이 필요한 작업은 사용자 승인을 받은 경우에만 다음 단계로 이동합니다.

## 3. 단계별 입력·작업·결과·검수

### 3-1. NotebookLM — 문서 기반 질의와 지식 정리

목표: 흩어진 기획 자료에서 기능의 배경, 기존 정책, 용어와 미결 질문을 근거와 함께 정리합니다.

| 구분 | 내용 |
|---|---|
| 입력물 | 기획서, 회의록, PDF, 참고 서비스 자료, 정책 문서, 과거 결정 기록, 사용자 질문 |
| 작업 | 관련 문서 검색, 용어 통합, 중복·충돌 탐색, 결정 이력 정리, 문서 근거가 있는 답변 작성 |
| 결과물 | 출처가 표시된 요구사항 후보, 정책 목록, 용어 정의, 문서 간 충돌, 미결 질문 |
| 검수 기준 | 모든 핵심 주장에 출처가 있음; 사실과 제안을 구분함; 충돌을 숨기지 않음; 최신 코드 상태를 안다고 가정하지 않음 |

다음 단계 인계 필수 정보:

- 사용한 문서명, 날짜 또는 버전
- 해결하려는 사용자 문제
- 문서에서 확인된 정책과 근거 위치
- 서로 충돌하는 문서 내용
- 확정된 사항과 사용자 결정이 필요한 사항
- 저장소 코드에서 재검증해야 할 주장

진행 금지 조건:

- 출처 없이 기능이나 정책을 창작한 경우
- 충돌하는 정책을 임의로 하나로 확정한 경우
- 문서의 기능 설명을 현재 구현 상태로 오인한 경우

### 3-2. ChatGPT — 기능 기획·문서·검증 설계

목표: NotebookLM의 자료와 사용자 요청을 구현 가능한 기능 정의와 검증 기준으로 바꿉니다.

| 구분 | 내용 |
|---|---|
| 입력물 | NotebookLM 인계, 사용자 요청, 관련 REQUIREMENTS·DATABASE·ROUTES 발췌, 기존 UX·정책 결정 |
| 작업 | 대상 사용자와 시나리오 정의, 범위·제외 범위 설정, 상태 전이·권한·예외 분석, UX 흐름 설계, 성공 조건 작성 |
| 결과물 | 기능 명세, 사용자 시나리오, 확정·미정 정책, 데이터·권한 검토 질문, 수용 기준, 테스트 시나리오 |
| 검수 기준 | 구현과 미구현을 구분함; 사용자 유형이 명확함; 골든 패스와 실패 경로가 있음; DB·RLS 추측은 재검증 항목으로 표시함 |

Claude Code/Codex 인계 필수 정보:

- 작업 목표와 대상 사용자
- 현재 문제와 기대 동작
- 포함 범위, 제외 범위, 변경 금지 영역
- 확정된 정책과 미결 정책
- 정상·빈 상태·오류·권한 없음 시나리오
- 수용 기준
- 관련 문서·화면·데이터 후보
- 코드에서 반드시 검증할 가정

검수 게이트:

- 모호한 정책이 결과를 크게 바꾸면 사용자 결정을 받습니다.
- 데이터 삭제, 기존 동작 변경, 여러 화면에 걸친 구조 변경 가능성을 표시합니다.
- ChatGPT가 제시한 파일명·테이블·함수는 구현자가 원본 코드로 다시 확인해야 합니다.

### 3-3. Claude Code 또는 Codex — 저장소 검증과 구현

목표: 인계된 명세를 현재 저장소에 맞춰 재검증하고 실제 코드·SQL·문서를 변경합니다.

| 구분 | 내용 |
|---|---|
| 입력물 | ChatGPT 기능 명세, NotebookLM 근거, 사용자 승인, 현재 Git 상태, 저장소 코드와 문서, 기존 Graphify 결과 |
| 작업 | `git status` 확인, 관련 `app/`·`lib/`·SQL 조사, 영향 범위 분석, 구현 계획, 필요한 승인, 최소 범위 수정, 타입·RLS·RPC 반영 |
| 결과물 | 코드·SQL·설정 변경, migration 파일, 테스트 가능한 로컬 상태, 변경된 기능의 1차 문서 반영, 검증 계획 |
| 검수 기준 | 실제 코드 근거와 일치함; 요청 범위를 벗어나지 않음; 기존 변경을 보존함; 비밀키가 없음; DB 변경은 새 migration으로 작성됨 |

구현 전 필수 확인:

1. [REQUIREMENTS.md](./REQUIREMENTS.md)의 기능 상태
2. [ROUTES.md](./ROUTES.md)의 실제 화면과 사용자 유형
3. [DATABASE.md](./DATABASE.md)의 보호 테이블, RPC, RLS, trigger
4. `page.tsx → lib 함수 → table/RPC → RLS/trigger` 연결
5. 기존 Graphify 결과의 생성 시점과 현재 구조 일치 여부

구현 중 규칙:

- NotebookLM·ChatGPT의 결론을 코드 확인 없이 그대로 반영하지 않습니다.
- 복잡한 영향 범위는 기존 Graphify 그래프로 탐색할 수 있지만 코드·SQL 원본으로 재검증합니다.
- `schema.sql`을 직접 migration처럼 수정하지 않고 새 `add_*.sql` 또는 `fix_*.sql`을 작성합니다.
- 사용자 승인 없는 파괴적 SQL, 대규모 리팩터링, push·배포는 수행하지 않습니다.
- 기능 상태가 달라지면 관련 문서를 1차로 함께 수정합니다. 최종 배포 결과와 commit 정보는 7단계에서 확정합니다.

로컬 테스트 단계 인계 필수 정보:

- 변경 목적과 파일 목록
- 주요 구현 결정
- 변경된 테이블·RPC·RLS·trigger
- migration과 환경변수 필요 여부
- 예상 사용자 시나리오
- 알려진 제한
- 실행해야 할 검증 명령과 수동 테스트

### 3-4. 로컬 테스트 — 기능·build·diff 검수

목표: GitHub에 올리기 전에 로컬 코드가 요구사항을 충족하고 기존 핵심 흐름을 깨뜨리지 않는지 확인합니다.

| 구분 | 내용 |
|---|---|
| 입력물 | 구현된 작업 트리, 수용 기준, 테스트 시나리오, migration, 로컬 환경변수 |
| 작업 | 골든 패스·예외 수동 테스트, 역할별 권한 확인, `npm run build`, 필요 시 `npm run dev`, `git diff --check`, diff·status 검토 |
| 결과물 | 테스트 결과, build 결과, 재현 전후 비교, 미실행 검증, diff 요약, GitHub 전달 가능 상태 |
| 검수 기준 | `npm run build` 성공; 요구사항의 성공 조건 충족; 주요 회귀 없음; 미실행 항목과 이유가 명시됨; 범위 밖 변경 없음 |

권장 테스트 매트릭스:

| 영역 | 최소 확인 |
|---|---|
| 공통 UI | 로딩, 빈 목록, 오류, 뒤로가기, 빠른 중복 요청 |
| 회원 | 비로그인, 대표·추가 프로필, 본인 데이터만 접근 |
| 매니저 | 소속 없음, 오너, 제한된 역할, 다른 센터 데이터 |
| 플랫폼 운영자 | 운영자·비운영자 접근 |
| 예약 | 예약, 대기, 취소, 마감, 수강권 차감·복구 |
| 결제·주문 | `pending` 생성, 중복 발급 방지, 실제 PG 미연동 안내 |
| DB | migration 성공, RLS read/write, 기존 행 영향 |

GitHub 진행 금지 조건:

- build 실패
- 재현되지 않은 버그를 추측으로 수정한 상태
- 필요한 migration이 없거나 의존성이 기록되지 않은 상태
- 비밀키·`.env*`가 diff나 staging에 포함된 상태
- 사용자 승인 없이 범위가 확대된 상태

### 3-5. GitHub — 버전 관리와 원격 검수

목표: 검증된 변경을 추적 가능한 작은 단위로 기록하고 리뷰·배포의 원격 기준선을 만듭니다.

| 구분 | 내용 |
|---|---|
| 입력물 | build가 통과한 작업 트리, diff 요약, 테스트 결과, migration·문서 변경, 사용자 commit/push 요청 |
| 작업 | 변경 검토, 논리적 단위 staging·commit, branch·commit SHA 확인, 요청 시 push와 pull request |
| 결과물 | commit SHA, 원격 branch, pull request와 리뷰 기록, Vercel이 참조할 배포 기준선 |
| 검수 기준 | 한 commit이 한 논리적 변경을 담음; 메시지가 무엇과 왜를 설명함; 테스트·migration·문서 상태가 기록됨; 비밀정보가 없음 |

Vercel 인계 필수 정보:

- branch와 commit SHA
- Preview 또는 Production 대상
- 변경 목적과 사용자 영향
- build·수동 테스트 결과
- 필요한 환경변수 키 이름(값 제외)
- migration 파일과 운영 적용 여부
- 알려진 제한과 롤백 고려사항

주의:

- commit은 push를 뜻하지 않습니다.
- push는 배포 성공을 뜻하지 않습니다.
- GitHub에 migration 파일이 있어도 Supabase에 적용된 것은 아닙니다.
- push와 pull request는 사용자 요청 또는 승인 범위 안에서 수행합니다.

### 3-6. Vercel — 배포와 배포 후 확인

목표: 지정한 GitHub commit을 Preview 또는 Production 환경에 빌드·배포하고 실제 배포 상태를 확인합니다.

| 구분 | 내용 |
|---|---|
| 입력물 | GitHub branch·commit SHA, 배포 환경, Vercel 프로젝트 연결, 환경변수, 별도로 적용된 Supabase migration |
| 작업 | Vercel build, 배포 상태·로그 확인, URL 확인, 배포 환경에서 골든 패스·핵심 오류 확인 |
| 결과물 | 배포 URL, 환경, commit SHA, 성공·실패 상태, 핵심 로그, 배포 후 테스트 결과 |
| 검수 기준 | 의도한 commit이 배포됨; build 성공; 필수 환경변수가 있음; 핵심 화면이 열림; API·Supabase 오류가 없음; migration 상태가 명확함 |

현재 저장소 기준 주의:

- `vercel.json`과 `.vercel/`이 없으므로 GitHub-Vercel 연결 여부와 배포 브랜치는 **확인 필요**입니다.
- 설정 파일 부재만으로 Vercel 미연결을 단정할 수 없습니다.
- Vercel 배포는 Supabase migration을 자동 적용한다고 가정하지 않습니다.
- Preview 성공을 Production 배포 승인으로 간주하지 않습니다.
- 실제 PG, OAuth Provider, Realtime, pg_cron은 별도 운영 설정입니다.

배포 실패 시:

1. 실패한 환경·commit·로그를 기록합니다.
2. 환경변수, build, migration, 런타임 오류를 구분합니다.
3. Claude Code/Codex로 되돌려 최소 수정 후 3~6단계를 반복합니다.
4. 실패 배포를 완료로 문서화하지 않습니다.

최종 단계 인계 필수 정보:

- 배포 환경과 URL
- 배포 branch·commit SHA
- Vercel build 결과
- 배포 후 확인한 시나리오
- Supabase migration·Realtime·Auth 설정 상태
- 실패 또는 미확인 항목

### 3-7. Graphify 및 문서 갱신 — 최종 동기화

목표: 배포된 코드 기준으로 구조 시각화와 프로젝트 문서를 동기화하고 다음 작업자가 추측 없이 이어받게 합니다.

| 구분 | 내용 |
|---|---|
| 입력물 | 최종 commit SHA, 배포 URL·상태, 구현·테스트 결과, 변경 파일, migration 적용 상태, 남은 작업 |
| 작업 | 구조 변경 여부 판단, Graphify 갱신, 문서별 책임에 맞게 상태·이력·TODO 갱신, 최종 diff 확인 |
| 결과물 | 최신 `graphify-out/`, 갱신된 문서, CHANGELOG 기록, TODO 후속 항목, 완결된 작업 인계 |
| 검수 기준 | 문서가 배포된 commit과 일치함; 구현·미완성·확인 필요·운영 설정 필요 상태가 정확함; 중복 없이 담당 문서에 기록됨 |

Graphify 처리:

```bash
graphify update .          # 파일·모듈 관계 빠른 갱신
graphify cluster-only .    # 커뮤니티·리포트 재생성, 비용 발생 가능
```

- 파일 추가·삭제·이동 또는 새 모듈 의존성이 있으면 `graphify update .` 필요 여부를 확인합니다.
- `cluster-only`는 분류·리포트까지 다시 만들 필요가 있고 사용자 확인을 받은 경우에만 실행합니다.
- 단순 문구·스타일 변경처럼 구조가 바뀌지 않았다면 갱신하지 않은 이유를 기록합니다.
- Graphify 결과는 코드 구조의 보조 자료이며 런타임·RLS 검증을 대신하지 않습니다.

## 4. 단계별 진행 상태

작업 보고에서는 아래 상태를 사용합니다.

| 상태 | 의미 |
|---|---|
| `대기` | 입력 또는 사용자 결정을 기다림 |
| `진행 중` | 해당 단계 작업 중 |
| `검수 필요` | 결과물은 있으나 검수 기준을 아직 통과하지 않음 |
| `완료` | 검수 기준을 통과하고 다음 단계 인계가 준비됨 |
| `건너뜀` | 사용자 범위상 수행하지 않았으며 이유를 기록함 |
| `차단됨` | 권한, 환경, 외부 설정 또는 반복 실패로 진행할 수 없음 |

예:

```text
NotebookLM: 완료
ChatGPT: 완료
Claude Code/Codex: 완료
로컬 테스트: 완료
GitHub: commit 완료 / push 건너뜀(사용자 요청 없음)
Vercel: 건너뜀(push 없음)
Graphify: 건너뜀(구조 변경 없음)
문서 갱신: 완료
```

## 5. 표준 완료 조건

작업은 요청 범위에 해당하는 아래 조건이 충족되어야 완료로 보고합니다.

- 요구사항과 대상 사용자가 명확합니다.
- 외부 문서의 주장이 실제 코드·SQL로 재검증되었습니다.
- 요청 범위의 코드·SQL·문서가 구현되었습니다.
- 로컬 테스트와 `npm run build` 결과가 기록되었습니다.
- Git 상태와 diff가 검토되었습니다.
- commit·push·배포 여부가 서로 구분되어 있습니다.
- 배포했다면 환경·URL·commit과 배포 후 확인 결과가 있습니다.
- migration과 운영 Supabase 적용 여부가 구분되어 있습니다.
- 구조 변경 시 Graphify 처리 여부가 기록되었습니다.
- REQUIREMENTS·DATABASE·ROUTES·TODO·CHANGELOG가 각자의 책임에 맞게 동기화되었습니다.
- 다음 작업자가 확인해야 할 미결 사항과 운영 설정이 남아 있습니다.
