# 수동 QA 체크리스트 — 담당 강사 복수 지정 + 수강권 허용 정책 변경

대상 브랜치: `feature/social-auth-notifications-attendance-dashboard`
관련 SQL: `add_class_trainers_pass_selection_mode_draft_proposed.sql`(적용 완료, 2026-08-11)
관련 코드: `app/manager/classes/page.tsx`, `app/reservation/page.tsx`, `lib/classes.ts`, `lib/reservations.ts`
자동 테스트로 이미 커버되는 항목도, 실제 브라우저·실제 데이터로 한 번은 눈으로 확인하는 것을 권장합니다.

## 준비

- [ ] 관리자 계정으로 `/manager/classes` 접속, 스태프가 1명 이상(오너 포함) 등록된 센터 선택
- [ ] 그 센터에 pass 상품이 2개 이상 등록돼 있는지 확인(0개/1개/여러 개 케이스를 모두 보려면 최소 2개 필요)
- [ ] 다른 센터 계정(비교용) 하나 더 준비 — "타 센터 스태프 차단" 확인용

## 1. 담당 강사 복수 지정

- [ ] **후보 목록**: 수업 등록/수정 시트의 "담당 강사" 섹션에 그 센터의 **active** 스태프만 뜨는지 확인. `pending`/`suspended` 상태 스태프가 있다면 목록에 안 보여야 함
- [ ] **0명 저장**: 강사를 하나도 선택하지 않고 저장 → 정상 저장되는지(강사 지정은 필수 아님)
- [ ] **1명 저장**: 강사 1명 선택 후 저장 → 재진입 시 그 1명이 체크된 상태로 보이는지
- [ ] **복수 저장**: 강사 2명 이상 선택 후 저장 → 재진입 시 전부 체크된 상태로 보이는지
- [ ] **수정(교체)**: 이미 강사가 지정된 수업을 열어 다른 강사로 바꿔 저장 → 이전 강사는 해제되고 새 강사만 남는지
- [ ] **전원 해제**: 강사가 지정된 수업에서 전부 체크 해제 후 저장 → 재진입 시 전부 해제 상태로 보이는지
- [ ] **타 센터 스태프 차단(RLS)**: (개발자 도구 없이 직접 재현은 어려움 — 아래 "자동 테스트로 대체" 참고) `class-trainers-and-pass-selection-mode.test.ts`의 RLS 케이스가 CI에서 통과하는지로 대체 확인
- [ ] **반복 수업 생성**: "매주 반복 등록" 켜고 강사 2명 선택 후 등록 → 생성된 여러 수업을 각각 열어 강사가 전부 동일하게 반영됐는지
- [ ] **수업 복사**: "스케줄 복사"로 강사가 지정된 수업을 다른 달에 복사 → 복사된 수업을 열어 원본과 동일한 강사가 지정돼 있는지
- [ ] **회원 화면 노출**: 강사가 지정된 수업을 회원 예약 화면(`/reservation`)에서 확인 → 강사 이름이 표시되는지(1명이면 이름만, 2명 이상이면 "이름 외 N명" 형식인지)
- [ ] **강사 미지정 수업**: 강사가 없는 수업은 회원 화면에 강사 관련 표시가 아예 안 뜨는지(빈 줄/이상한 문구 없이 자연스럽게 생략)

## 2. 수강권 허용 정책 변경

> 이번에 UI를 SQL 원래 설계대로 맞췄습니다: **선택 0개는 저장 불가**, "전체 선택" 버튼으로만 명시적 전체허용을 표현합니다. 새 수업/처음 여는 수업은 기본적으로 **모든 수강권이 이미 체크된 상태**로 시작합니다(예전의 "아무것도 안 고르면 전체허용"과 겉보기 결과는 같지만 상호작용이 다릅니다).

- [ ] **신규 수업 기본 상태**: "수업 등록" 시트를 열면 "예약 가능 수강권" 섹션의 모든 pass가 이미 체크돼 있고, 안내 문구가 "모든 수강권으로 예약 가능해요"인지
- [ ] **0개 선택 차단**: 체크를 전부 해제("전체 해제" 클릭)한 상태에서 저장 시도 → 저장이 안 되고 "최소 1개 이상 선택해주세요" 안내가 뜨는지 (반복 등록/일반 등록/수정 세 경로 모두 확인)
- [ ] **일부만 선택**: pass 중 일부만 선택하고 저장 → 안내 문구가 "N개 수강권만 이 수업에 사용할 수 있어요"로 바뀌는지, 저장 후 재진입 시 그 N개만 체크돼 있는지
- [ ] **전체 선택 버튼**: 일부만 선택된 상태에서 "전체 선택" 버튼 클릭 → 모든 chip이 체크되고 안내 문구가 "모든 수강권" 문구로 돌아오는지
- [ ] **전체 해제 버튼**: 전체 선택 상태에서 "전체 해제" 버튼 클릭 → 모든 chip이 해제되고 경고 문구(저장 불가 안내)가 뜨는지
- [ ] **all 모드 — schedule_rules 그대로 적용**: 전체 허용 상태로 저장한 수업에서, 특정 수강권에 요일/시간 예약조건이 걸려 있고 그 수업 요일/시간과 안 맞으면 "실제로 쓸 수 없어요" 경고(danger)가 뜨는지 + 회원 화면에서 그 수강권으로 실제 예약 시도하면 거부되는지
- [ ] **selected 모드 — override 적용**: 특정 pass만 선택해 저장한 수업에서, 그 pass에 요일/시간 예약조건이 걸려 있고 안 맞아도 override 안내(info, "직접 지정이 우선")가 뜨는지 + 회원 화면에서 그 수강권으로 실제 예약이 **성공**하는지
- [ ] **selected 모드 — 미선택 수강권 차단**: 특정 pass 1~2개만 선택한 수업에서, 회원이 선택 안 된 다른 pass로 예약 시도(직접 API 호출이 아니라 화면상 그 pass가 애초에 목록에 안 보이는지) → 목록에 안 보이는지 확인
- [ ] **기존(migration 이전) 수업 회귀 없음**: 이번 SQL 적용 전부터 있던, `class_allowed_products`에 특정 상품이 지정된 기존 수업 하나를 열어 → 여전히 "특정 수강권 지정" 상태로 보이는지(전체 체크가 아님), 그 상품으로 회원 예약이 여전히 되는지
- [ ] **기존 "전체허용" 수업 회귀 없음**: 이번 SQL 적용 전부터 있던, 한 번도 수강권을 지정한 적 없는 기존 수업 하나를 열어 → 전체 체크 상태로 보이는지, 회원이 보유한 모든 수강권으로 여전히 예약되는지
