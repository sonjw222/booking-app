# Security

## 1. 보안 목표

보호 대상은 사용자 계정, 센터별 운영·고객·예약 데이터, 인증 토큰, 권한 및 감사 기록이다. 주요 위협은 센터 간 데이터 노출, 계정 탈취, 초대 탈취, OAuth 계정 오연결, 세션 재사용, 예약 조작, 개인정보 유출이다.

## 2. 인증

- 비밀번호는 최신 권장 KDF(Argon2id 우선)와 사용자별 salt로 해시한다.
- 최소 길이는 12자를 기본으로 하며 긴 passphrase와 password manager를 허용한다.
- 유출 비밀번호 차단을 지원하되 비밀번호 원문/해시를 외부에 보내지 않는다.
- 로그인 실패는 IP와 계정 식별자 기준 rate limit, 점진적 지연, 위험 기반 추가 확인을 적용한다.
- 이메일 인증, 비밀번호 재설정, 초대 토큰은 CSPRNG로 생성하고 원문을 저장하지 않으며 짧은 만료·1회 사용을 강제한다.
- 비밀번호 변경, 계정 연결/해제, 전체 세션 철회는 최근 인증을 요구한다.

## 3. 소셜 로그인과 Account Linking

- OAuth 2.0 Authorization Code + PKCE 및 OIDC를 사용하고 `state`, `nonce`, issuer, audience, 서명을 검증한다.
- 공급자의 `(issuer/provider, subject)`를 기본 식별자로 사용한다. 이메일은 보조 속성이다.
- 공급자가 검증한 이메일이라도 기존 계정과 동일하다는 이유만으로 자동 연결하지 않는다.
- 연결은 이미 로그인한 사용자의 재인증으로 시작하거나, 충돌 시 기존 계정 인증 후 짧은 수명의 linking ticket으로 완료한다.
- linking ticket은 사용자, 공급자, 시작 세션에 결박하고 1회 사용한다.
- 마지막 로그인 수단 unlink는 금지하며 연결/해제는 사용자에게 알리고 감사한다.

## 4. 세션과 기기

- Access Token은 짧게, Refresh Token은 장기이되 매 사용 시 회전한다.
- Refresh Token은 해시 저장하고 token family를 추적한다.
- 이미 사용된 Refresh Token이 재사용되면 해당 family 전체를 철회하고 보안 이벤트를 발생시킨다.
- 비밀번호 재설정, 계정 정지, 중대한 권한 변경은 관련 세션을 철회한다.
- 쿠키는 `HttpOnly; Secure; SameSite=Lax/Strict`를 기본으로 하고 필요한 교차 사이트 흐름은 최소 범위로 예외 처리한다.
- 쿠키 인증 쓰기 요청은 CSRF 토큰/Origin 검증을 적용한다.
- 세션 목록에는 정확한 IP 대신 최소화된 기기·최근 활동 정보를 표시한다.
- 서버에서 철회 여부를 확인할 수 없는 완전 무상태 장기 토큰은 사용하지 않는다.

## 5. 권한과 멀티센터 격리

- 모든 센터 API는 인증 후 Membership 상태와 권한을 서버에서 평가한다.
- `center_id`는 클라이언트 body 값이 아니라 검증된 경로/컨텍스트에서 주입한다.
- ID만으로 조회하는 저장소 메서드를 금지하고 센터 소유 데이터는 `(center_id, id)`로 조회한다.
- Platform Admin 권한은 별도 영역과 강한 인증으로 보호한다.
- 마지막 Owner 제거/강등, 자기 권한 상승, 허용 범위를 넘는 초대를 차단한다.
- 캐시 키, 파일 경로, 검색 인덱스, 작업 큐에도 `center_id` 경계를 포함한다.

## 6. 애플리케이션 보안

- 입력 스키마 검증, 출력 인코딩, parameterized query를 사용한다.
- CSP, HSTS, `X-Content-Type-Options`, `Referrer-Policy`, frame 제한 등 보안 헤더를 적용한다.
- CORS는 명시적 origin만 허용하고 credential과 wildcard를 함께 사용하지 않는다.
- 파일 업로드 도입 시 MIME/확장자/크기 검사, 악성코드 스캔, 비공개 저장소, 서명 URL을 사용한다.
- SSRF 방지를 위해 외부 URL fetch는 allowlist와 사설망 차단을 적용한다.
- 의존성/컨테이너/비밀값 스캔을 CI에 포함하고 운영 비밀값을 저장소에 커밋하지 않는다.

## 7. 개인정보와 암호화

- 전송은 TLS, 저장은 관리형 암호화를 사용한다.
- 특히 민감한 필드는 애플리케이션 수준 암호화를 검토하고 키는 별도 KMS에서 순환한다.
- 로그, 오류, 분석, 고객지원 화면에서 토큰·비밀번호·전체 이메일/전화번호를 마스킹한다.
- 수집 목적, 동의, 보존, 삭제 및 데이터 내보내기 정책을 제품 출시 전에 확정한다.

## 8. 감사 및 대응

반드시 기록할 이벤트:

- 로그인 성공/실패, 로그아웃, Refresh 재사용
- 비밀번호 재설정 요청/완료, 이메일 변경/인증
- 소셜 identity 연결/해제
- 기기/세션 생성·철회·전체 철회
- 센터 생성/정지, 초대 생성/재전송/취소/수락
- 역할·Membership 변경
- 예약의 관리자 변경/취소
- 보안 설정 및 Platform Admin 행위

감사 로그는 append-only이며 행위자, 대상, 센터, 결과, 시간, 요청 상관관계, 변경 필드 요약을 남긴다. 비밀값과 전체 PII는 남기지 않는다.

사고 대응은 탐지 → 격리/세션 철회 → 영향 범위 확인 → 복구 → 통지 판단 → 사후 분석 순으로 수행하며 담당자와 연락 체계는 출시 전에 지정한다.

## 9. 출시 보안 게이트

- 권한 매트릭스와 센터 교차 접근 자동 테스트 통과
- OAuth redirect allowlist 및 공급자 설정 검토
- 비밀값/의존성/정적 분석과 고위험 취약점 조치
- 세션 철회·재설정·초대 만료 검증
- 백업 복구와 사고 대응 tabletop 수행
- 개인정보 처리방침 및 보존 설정 승인
