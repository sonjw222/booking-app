이 문서는 도구별로 “무엇을 맡는가”, “무엇을 해서는 안 되는가”, “다음 도구에 무엇을 넘겨야 하는가”를 정의합니다. 실제 저장소 파일을 변경하는 작업은 Claude Code 또는 Codex가 수행합니다.

## 2. 전체 작업 흐름

```text
NotebookLM ── 문서 기반 질의·지식 정리 ─┐
                                         ├─→ ChatGPT ── 기획·문서·검증
기획 자료·사용자 결정 ──────────────────┘             │
                                                       ▼
                                              구현 인계 패키지
                                                       │
                          Graphify ── 구조·흐름 시각화 ─┤
                                                       ▼
                                             Claude Code / Codex
                                          실제 구현·수정·테스트·문서화
                                                       │
                                                       ▼
                                                   GitHub
                                         버전 관리·리뷰·원격 기준선
                                                       │
                                                       ▼
                                                   Vercel
                                              빌드·배포·배포 상태
```

Supabase는 앱의 DB·Auth·Storage·Realtime 실행 환경입니다. 이 흐름에서 별도 기획 도구가 아니라 Claude Code/Codex가 코드와 SQL을 통해 다루는 백엔드 대상입니다. 운영 DB 변경과 파괴적 작업은 사용자 승인 및 별도 적용 확인이 필요합니다.

## 3. 공통 원칙

1. 외부 도구의 결론보다 현재 저장소의 `app/`, `lib/`, SQL을 우선합니다.
2. “구현됨”, “미완성”, “확인 필요”, “운영 설정 필요” 상태는 [REQUIREMENTS.md](./REQUIREMENTS.md)의 판정 기준을 따릅니다.
3. 저장소 밖 상태를 추측하지 않습니다. 운영 Supabase, GitHub 설정, Vercel 연결 상태는 확인 전까지 **확인 필요**입니다.
4. 한 도구가 다음 도구의 책임을 대신했다고 가정하지 않습니다. 기획 완료는 구현 완료가 아니고, 로컬 build 성공은 배포 성공이 아닙니다.
5. 모든 인계는 출처, 결정, 미결 사항, 검증 범위를 포함해야 합니다.
6. 파괴적 DB 작업, 비밀키 처리, 기존 동작 변경, push와 배포는 사용자 권한과 저장소 규칙을 따릅니다.
7. 문서와 코드가 다르면 Claude Code/Codex가 코드를 확인해 문서를 갱신합니다.

## 4. 도구별 책임과 금지 작업

### 4-1. ChatGPT — 기획·문서·검증

담당:

- 사용자 요구를 기능, 정책, UX, 예외 상황으로 구조화
- 요구사항 문서 초안과 문서 구조 설계
- 구현 계획, diff, SQL/RLS, 테스트 결과의 독립 검토
- 누락된 상태 전이, 권한, 데이터 정합성, UX 위험 식별
- NotebookLM 결과를 제품 결정과 구현 가능한 요구사항으로 정리
- 구현 후 결과가 요구사항을 충족하는지 검증 기준으로 재검토

해서는 안 되는 작업:

- 현재 저장소를 보지 않은 상태에서 기능이 구현됐다고 단정
- 테이블 존재만으로 화면과 제품 흐름이 완성됐다고 판단
- 운영 Supabase migration, Vercel 배포, GitHub 상태를 확인 없이 완료 처리
- 코드 위치, 함수명, 라우트, 컬럼을 추측해 구현 지시
- 검증되지 않은 초안을 Claude Code/Codex가 그대로 실행해야 하는 확정 명세로 표현
- 사용자 결정이 필요한 정책을 임의로 확정

Claude Code/Codex에 넘길 필수 정보:

- 문제 또는 목표
- 대상 사용자와 사용자 시나리오
- 구현 범위와 제외 범위
- 확정된 정책과 아직 미정인 정책
- 성공 조건과 실패·예외 조건
- 관련 문서·화면·코드 근거
- 검증해 달라는 위험 항목

### 4-2. Claude Code와 Codex — 구현·수정

두 도구는 같은 책임 범주를 가집니다. 어느 도구가 작업하든 현재 저장소를 직접 읽고 수정하며, 이전 도구의 산출물을 코드로 재검증합니다.

담당:

- `app/`, `lib/`, SQL, 설정과 관련 문서를 직접 조사
- 요구사항을 현재 구현 상태와 대조
- 영향 범위와 권한·데이터 흐름 분석
- 코드·SQL·문서의 실제 생성과 수정
- 로컬 테스트, `npm run build`, 가능한 수동 UI 확인
- diff 검토, 변경 요약, 문서 갱신
- 사용자 요청이 있을 때 Git commit·push 수행
- 구조 변경 시 Graphify 갱신 필요 여부 판단

해서는 안 되는 작업:

- 사용자 범위를 벗어난 대규모 리팩터링
- 재현·근거 없이 추측으로 버그 수정
- 기존 `schema.sql`을 현재 migration처럼 직접 수정
- 사용자 승인 없는 `DROP`, `TRUNCATE`, 컬럼 삭제, 광범위한 `DELETE`·`UPDATE`
- 비밀키나 `.env.local` 값을 코드·문서·Git에 저장
- build 실패를 `any`, `@ts-ignore` 등으로 숨김
- 운영 DB에 SQL 파일이 적용됐다고 저장소만 보고 단정
- 사용자 요청 없는 push·배포
- 다른 작업자의 기존 변경을 임의로 되돌림

GitHub 또는 다음 구현자에게 넘길 필수 정보:

- 변경 목적과 사용자 영향
- 변경한 파일 목록
- 주요 설계 결정과 대안 선택 이유
- DB/RLS/RPC/trigger 영향
- 실행한 검증과 결과
- 실행하지 못한 검증과 이유
- 남은 문제와 운영 설정 필요 사항
- migration 적용 순서 또는 의존성
- diff 요약과 현재 Git 상태

### 4-3. NotebookLM — 문서 기반 질의·지식 관리

담당:

- 기획서, 회의록, 정책 문서, 참고 자료의 검색과 요약
- 여러 문서 사이의 공통점·충돌·결정 이력 정리
- 제품 용어, 정책, 배경지식의 장기 지식베이스 관리
- 문서 근거가 있는 질문에 출처와 함께 답변
- 미결 정책과 추가 질문 목록 작성

해서는 안 되는 작업:

- 저장소의 최신 코드 상태를 알고 있다고 가정
- 문서에 없는 기능을 구현됐다고 판단
- 코드 수정, SQL 실행, Git 작업, 배포 수행
- 오래된 문서를 현재 구현의 최종 진실로 취급
- 출처 없이 정책을 창작하거나 사용자 결정을 대신함

ChatGPT 또는 Claude Code/Codex에 넘길 필수 정보:

- 사용한 문서와 버전·날짜
- 질문과 답변 요약
- 근거가 된 원문 위치
- 문서 간 충돌
- 확정된 결정과 미결 질문
- 코드에서 재검증해야 할 주장

### 4-4. Graphify — 구조와 흐름 시각화

담당:

- 파일·모듈·심볼 사이 의존관계 시각화
- 기능별 커뮤니티와 허브 탐색
- 변경 대상에서 다른 화면·함수로 이어지는 영향 경로 탐색
- 복잡한 버그와 구조 변경의 조사 범위 보조

주요 사용:

```bash
graphify explain "app/reservation/page.tsx"
graphify path "reservations.ts" "reservation/page.tsx"
graphify update .
graphify cluster-only .
```

`graphify path`가 디렉터리 접두사가 있는 노드를 찾지 못하면 파일명 또는 `explain` 결과의 `Node:` 값을 사용합니다.

해서는 안 되는 작업:

- 그래프 결과만으로 실제 런타임 동작이나 권한을 확정
- 코드·SQL 원본 확인 없이 영향 범위가 완전하다고 보장
- 오래된 그래프를 현재 구조로 간주
- 요구사항 결정, 코드 수정, 테스트 통과 판정
- 비용이 발생하는 재클러스터링을 사용자 확인 없이 실행

Claude Code/Codex에 넘길 필수 정보:

- 사용한 그래프 생성 시점 또는 갱신 여부
- 실행한 명령
- 시작 노드와 도착 노드
- 발견한 주요 경로·허브
- 그래프가 놓칠 수 있는 동적 호출·SQL·RLS 영역
- 코드에서 직접 확인해야 할 후보 파일

### 4-5. GitHub — 버전 관리

담당:

- 저장소와 브랜치의 원격 기준선
- commit, branch, pull request와 코드 리뷰 기록
- 변경 이력과 협업 상태 공유
- Vercel이 연결된 경우 배포 트리거 제공

해서는 안 되는 작업:

- 문서·코드의 내용이 옳다고 자동 보장
- commit 존재만으로 build·QA·migration 적용 완료를 의미
- 승인되지 않은 코드나 비밀키 저장
- 여러 논리적 변경을 근거 없이 하나의 커밋으로 합침
- GitHub에 push됐다는 이유로 운영 DB도 갱신됐다고 간주

리뷰어·Vercel·다음 작업자에게 넘길 필수 정보:

- 브랜치와 commit SHA
- 변경 목적과 범위
- 주요 변경 파일
- build·테스트 결과
- migration 파일과 운영 적용 여부
- 환경변수 변경 여부
- 알려진 제한과 롤백 고려사항
- 배포 대상 브랜치 여부

### 4-6. Vercel — 배포

담당:

- 연결된 GitHub 브랜치의 Next.js build와 배포
- Preview·Production 배포 URL 제공
- 빌드 로그와 배포 상태 제공
- 배포 환경변수 적용

해서는 안 되는 작업:

- Supabase migration 자동 적용을 가정
- 로컬에서 검증되지 않은 변경을 안전하다고 판정
- 누락된 환경변수를 코드 기본값으로 임의 대체
- Preview 성공을 Production 승인으로 간주
- 배포 성공만으로 예약·결제·RLS·Realtime 동작을 보장
- 사용자 확인 없이 운영 배포를 진행

사용자·Claude Code/Codex에 넘길 필수 정보:

- 배포 환경(Preview/Production)
- 배포한 branch와 commit SHA
- 배포 URL
- build 성공·실패 상태와 핵심 로그
- 사용된 환경변수 키 목록과 누락 여부(값은 공유하지 않음)
- migration·Supabase 설정의 별도 적용 필요 여부
- 배포 후 확인한 골든 패스와 실패 항목

## 6. 기능 개발 절차

```text
요구사항 정리 → 코드 기준선 확인 → 영향 범위 분석 → 구현 계획
→ 필요한 사용자 승인 → 코드·SQL 수정 → 테스트·build
→ 문서 갱신 → Graphify 갱신 판단 → diff 요약 → commit/push
```

### 6-1. 요구사항과 기준선

- ChatGPT·NotebookLM 산출물은 입력 자료이며 구현 명세의 최종 진실이 아닙니다.
- [REQUIREMENTS.md](./REQUIREMENTS.md)에서 현재 상태와 대상 사용자를 확인합니다.
- [ROUTES.md](./ROUTES.md)에서 실제 화면과 권한 처리 방식을 확인합니다.
- [DATABASE.md](./DATABASE.md)에서 현재 사용 객체, 보호 테이블, RPC와 중복 정의 위험을 확인합니다.

### 6-2. 영향 범위와 계획

- `page.tsx → lib 함수 → table/RPC → RLS/trigger` 순서로 추적합니다.
- 여러 파일·도메인에 걸치면 Graphify로 후보 경로를 찾고 코드 원본으로 재검증합니다.
- 변경 파일, 함수 시그니처, migration, 사용자 유형, 예외 상황을 계획에 포함합니다.

### 6-3. 승인

다음 작업은 구현 전에 사용자에게 범위와 영향을 알리고 필요한 승인을 받습니다.

- 새 테이블·컬럼, 타입·상태값 변경
- 기존 동작 또는 정책 변경
- 여러 화면에 걸친 구조 변경
- 데이터 삭제·백필·파괴적 SQL
- 비용이 발생하는 Graphify 재클러스터링
- push 또는 Production 배포

### 6-4. 구현과 검증

- 수정은 Claude Code/Codex가 [DEVELOPMENT_RULES.md](./DEVELOPMENT_RULES.md)에 따라 수행합니다.
- UI는 로그인, 권한 없음, 빈 목록, 로딩, 실패와 골든 패스를 확인합니다.
- DB 변경은 회원·매니저·오너·플랫폼 운영자 역할별 RLS를 확인합니다.
- 코드 변경 후 `npm run build`를 실행합니다.
- 자동 테스트가 없는 영역은 수동 테스트의 범위와 결과를 인계에 기록합니다.

### 6-5. 문서와 Git

- 기능 상태: [REQUIREMENTS.md](./REQUIREMENTS.md)
- 테이블·RPC·RLS·trigger: [DATABASE.md](./DATABASE.md)

- push는 사용자 요청이 있을 때만 수행합니다.

## 7. 버그 수정 절차

```text
재현 → 근거 수집 → 원인 분석 → 영향 범위 → 최소 수정
→ 회귀 테스트 → build → 문서·인계 → commit/push
```

- 재현되지 않으면 추측으로 수정하지 말고 필요한 조건을 `확인 필요`로 남깁니다.
- build 오류는 파일·라인과 최초 오류부터 확인합니다.
- RLS 문제는 관련 `fix_*.sql`, 현재 정책, 함수 중복 정의를 함께 확인합니다.
- 같은 패턴이 다른 화면·함수에 반복되는지 검색하고 필요하면 Graphify를 사용합니다.
- 버그와 무관한 리팩터링은 분리합니다.
- 수정 전후 재현 결과와 인접 기능 회귀 결과를 인계합니다.
- 알려진 TODO가 해결되면 상태를 갱신하고 CHANGELOG에 원인과 해결을 기록합니다.

## 8. DB 변경 절차

```text
현재 SQL 원본 확인 → 운영 상태 확인 필요 여부 판단 → migration 설계
→ 사용자 승인 → RLS·기존 데이터·중복 함수 검토
→ 새 migration 작성 → 코드 타입 반영 → 역할별 테스트
→ DATABASE/CHANGELOG 갱신 → 운영 적용 인계
```

- `schema.sql`만 최종 상태로 간주하지 않고 관련 `add_*.sql`, `fix_*.sql`을 모두 확인합니다.
- 같은 RPC가 여러 파일에서 `create or replace`되는지 검색합니다.
- 기존 `schema.sql` 대신 새 `add_<기능>.sql` 또는 `fix_<문제>.sql`을 작성합니다.
- 새 테이블에는 RLS 활성화와 정책을 같은 migration에 포함합니다.
- `NOT NULL` 컬럼은 기본값·백필·기존 행 영향을 계획합니다.
- 삭제 전 `app/`, `lib/`, 전체 SQL, RPC 내부 참조와 운영 데이터를 확인합니다.
- 함수 시그니처 변경 시 모든 호출자를 수정합니다.
- migration 파일 생성과 운영 Supabase 적용은 별도 상태입니다. 적용 전에는 **운영 설정 필요** 또는 **확인 필요**로 인계합니다.
