# AI_PLAYBOOK

Claude Code(또는 다른 AI 도구)가 이 저장소에서 작업할 때 따라야 하는 절차입니다.
상위 규칙은 [CLAUDE.md](../CLAUDE.md)에 있고, 이 문서는 그 규칙을 세 가지 작업 유형(기능 개발/버그 수정/DB 변경)에
맞춰 실제로 무엇을, 어떤 순서로, 어떤 명령으로 하는지 구체화한 것입니다.

각 단계에서 "승인"이라고 적힌 지점은 반드시 사용자의 명시적 확인을 받은 뒤에만 다음 단계로 넘어갑니다.

---

## 1. 기능 개발

```
요구사항 확인 → 영향 범위 분석 → 구현 계획 작성 → 사용자 승인
→ 코드 수정 → 테스트 → build → 문서 갱신 → Graphify 갱신 → 커밋
```

### 1-1. 요구사항 확인
- 사용자의 요청을 그대로 실행하지 말고, 관련된 기존 기능이 [docs/REQUIREMENTS.md](./REQUIREMENTS.md)에 이미 있는지 확인합니다.
  - 이미 구현된 기능이면: 왜 다시 요청하는지(버그인지, 확장인지) 파악합니다.
  - "미완성 기능" 표에 있는 항목이면: 왜 미완성인지 이유(예: PG 미연동, 스키마만 존재)를 먼저 파악하고 사용자에게 공유합니다.
- 요구사항이 NotebookLM/ChatGPT 등 외부 도구에서 정리되어 넘어온 경우, 그 산출물을 그대로 구현 계획으로 쓰지 말고
  이 저장소의 실제 코드/스키마와 맞춰 재검증합니다 — 외부 도구는 이 코드베이스의 최신 상태를 모릅니다([docs/WORKFLOW.md](./WORKFLOW.md) 참고).

### 1-2. 영향 범위 분석
- 수정할 화면(`app/**/page.tsx`)이 어떤 `lib/*.ts` 함수를 쓰는지, 그 함수가 어떤 Supabase 테이블/RPC를 건드리는지 추적합니다.
- 여러 파일에 걸친 변경이거나 어디까지 영향이 퍼지는지 확신이 없으면 Graphify를 사용합니다:
  ```bash
  graphify explain "app/reservation/page.tsx"     # 이 파일과 연결된 노드들 설명
  graphify path "reservations.ts" "reservation/page.tsx"   # 두 지점 사이 연결 경로
  ```
  - `graphify path`는 `lib/`, `app/` 같은 디렉터리 접두사를 붙이면 노드를 못 찾는 경우가 있습니다(확인됨) —
    파일명만(또는 `explain` 결과의 "Node:" 줄에 나오는 이름으로) 넣는 것이 안전합니다. `graphify explain`은 접두사를 붙여도 정상 동작합니다.
  - `graphify-out/GRAPH_REPORT.md`의 "Community Hubs" 목록에서 관련 커뮤니티(예: "Reservation Calendar", "Sales & Payments")를 먼저 훑으면 관련 파일을 빠르게 찾을 수 있습니다.
- 회원/매니저/플랫폼 운영자 중 어느 역할에 영향을 주는지 [docs/ROUTES.md](./ROUTES.md)에서 확인합니다 — 특히 이 프로젝트는
  프론트엔드가 권한별로 UI를 숨기지 않고 서버(RLS/RPC)에서만 막는 구조이므로, 권한 관련 기능은 서버 쪽 영향까지 함께 추적하세요.

### 1-3. 구현 계획 작성
- 바꿀 파일 목록, 각 파일에서 무엇을 바꿀지, 새 SQL 마이그레이션이 필요한지를 짧은 계획으로 정리합니다.
- 기존 함수 시그니처(파라미터/반환 타입)를 바꾸는 경우, 그 함수를 호출하는 모든 곳을 계획에 포함합니다.

### 1-4. 사용자 승인
- 계획을 제시하고 진행 여부를 확인받습니다. 특히 다음의 경우 승인 없이 진행하지 않습니다:
  - 새 테이블/컬럼 추가, 기존 컬럼 타입 변경
  - 여러 페이지에 걸친 변경
  - 기존 기능의 동작 방식 변경(단순 버그 수정이 아닌 경우)

### 1-5. 코드 수정
- [docs/DEVELOPMENT_RULES.md](./DEVELOPMENT_RULES.md)를 따릅니다(TypeScript `any` 금지, 기존 스타일 유지 등).
- 요청 범위를 벗어나는 리팩터링/이름 변경은 하지 않습니다(CLAUDE.md 규칙 13).

### 1-6. 테스트
- UI 변경이면 `npm run dev`로 실제 화면에서 골든 패스와 주요 예외 상황(비로그인, 권한 없음, 빈 목록 등)을 확인합니다.
- 이 프로젝트는 자동화된 테스트 스위트가 없으므로(확인됨), 수동 확인이 유일한 검증 수단입니다 — 스킵하지 마세요.

### 1-7. build
```bash
npm run build
```
- 실패하면 근본 원인을 고칩니다. 성공 전까지 다음 단계로 넘어가지 않습니다(CLAUDE.md 규칙 7).

### 1-8. 문서 갱신
- 새로 구현된 기능을 [docs/REQUIREMENTS.md](./REQUIREMENTS.md) "현재 구현된 기능"에 추가합니다.
- 새 라우트가 생겼으면 [docs/ROUTES.md](./ROUTES.md)에 추가합니다.
- 새 테이블/컬럼이 생겼으면 [docs/DATABASE.md](./DATABASE.md)에 추가합니다.
- [docs/CHANGELOG.md](./CHANGELOG.md)에 날짜와 함께 한두 줄로 기록합니다.

### 1-9. Graphify 갱신
- 새 파일 추가/삭제, 모듈 간 새로운 의존관계가 생겼다면 그래프가 낡습니다. 사용자에게 갱신 여부를 확인한 뒤:
  ```bash
  graphify update .          # 빠른 재추출, LLM 미사용 — 기본적으로 이것으로 충분
  graphify cluster-only .    # 커뮤니티 분류/리포트까지 다시 만들 때만 (LLM 호출 비용 발생)
  ```

### 1-10. 커밋
- `git status`, `git diff`로 변경 내역을 사람이 읽을 수 있게 요약해 사용자에게 보여줍니다(CLAUDE.md 규칙 11).
- 기능 단위로 작은 커밋을 만듭니다. `git push`는 사용자가 명시적으로 요청할 때만 합니다.

## 2. 버그 수정

```
재현 → 원인 분석 → 영향 범위 확인 → 최소 수정 → 회귀 테스트 → build → 문서 갱신 → 커밋
```

### 2-1. 재현
- 사용자가 준 재현 방법으로 실제로 문제를 재현합니다. 재현이 안 되면 추측으로 고치지 말고 재현 조건을 더 확인합니다.
- 빌드 실패 버그는 `npm run build` 출력의 파일/라인 번호부터 확인합니다(이 저장소에서 실제로 자주 발생하는 패턴:
  `useSearchParams()` + `Suspense` 누락, state 타입에 실제 사용하는 필드가 빠짐 — 과거 사례는 [docs/CHANGELOG.md](./CHANGELOG.md) 참고).

### 2-2. 원인 분석
- 증상이 아니라 근본 원인을 찾습니다. 이 저장소는 RLS 관련 회귀 버그 이력이 많으므로([docs/DATABASE.md](./DATABASE.md) 4절,
  [docs/TODO.md](./TODO.md) 참고), RLS/권한이 얽힌 버그라면 관련 `fix_*.sql` 이력을 먼저 훑어 같은 패턴이 반복되는지 확인합니다.
- 원인 파악이 안 되는 다중 파일 버그는 Graphify로 연관 노드를 탐색합니다(`graphify explain`).

### 2-3. 영향 범위 확인
- 이 버그의 원인이 되는 코드/설정을 다른 곳에서도 같은 패턴으로 쓰고 있는지 확인합니다(같은 실수가 여러 곳에 반복될 수 있음 — 실제로 `useSearchParams()` Suspense 누락은 한 번에 5개 페이지에서 동시에 발견된 전례가 있습니다).

### 2-4. 최소 수정
- 버그와 무관한 리팩터링/스타일 변경을 함께 넣지 않습니다. 수정 범위를 원인에 맞게 최소화합니다.

### 2-5. 회귀 테스트
- 고친 부분이 실제로 해결됐는지 재현 시나리오로 재확인하고, 근처의 관련 기능(같은 페이지/같은 테이블을 쓰는 다른 화면)이
  깨지지 않았는지 함께 확인합니다.

### 2-6. build
```bash
npm run build
```

### 2-7. 문서 갱신
- [docs/CHANGELOG.md](./CHANGELOG.md)에 무엇이 왜 고장났고 어떻게 고쳤는지 기록합니다.
- 이 버그가 [docs/TODO.md](./TODO.md)에 이미 알려진 문제로 있었다면 해당 항목을 제거하거나 "해결됨"으로 표시합니다.

### 2-8. 커밋
- `git diff`/`git status` 요약 후 커밋. push는 명시적 요청 시에만.

## 3. DB 변경

```
현재 스키마 확인 → migration 작성 → RLS 정책 확인 → 기존 데이터 영향 확인 → 코드 타입 반영 → 테스트 → 문서 갱신
```

### 3-1. 현재 스키마 확인
- [docs/DATABASE.md](./DATABASE.md)에서 관련 테이블의 현재 컬럼/관계를 확인하되, **최종 확인은 `schema.sql`과 관련
  `add_*.sql`/`fix_*.sql` 원본 파일로** 합니다(문서는 요약이라 최신 상태와 어긋날 수 있음).
- 같은 개념을 다루는 테이블이 이미 두 개 이상 있는지 확인합니다(이 저장소는 `point_transactions`/`point_accounts`처럼
  포인트 시스템이 이원화된 전례가 있습니다 — 확인 필요 상태로 문서에 남아 있음, [docs/DATABASE.md](./DATABASE.md) 1-3절 참고).

### 3-2. migration 작성
- 기존 `schema.sql`을 직접 고치지 않고 `add_<기능>.sql` 또는 `fix_<문제>.sql` 새 파일을 저장소 루트에 추가합니다.
- 파일 상단에 `-- ====...====` 구분선과 목적을 설명하는 한글 주석을 답니다(기존 파일들의 관례를 따름).
- 파괴적 구문(`DROP`, `TRUNCATE`, 컬럼 삭제, `WHERE` 없는 `DELETE`/`UPDATE`)이 포함되면 반드시 사용자 승인을 먼저 받습니다(CLAUDE.md 규칙 3).

### 3-3. RLS 정책 확인
- 새 테이블이면 `alter table ... enable row level security;`와 관련 정책을 **같은 파일**에 포함합니다.
- 정책 안에서 재귀적으로 호출되는 헬퍼 함수가 필요하면 기존 `my_account_id()` / `my_profile_ids()` / `is_platform_admin()` /
  `has_permission(center_id, permission_key)` 패턴을 재사용하고, 새 헬퍼는 `security definer`로 선언해 무한 재귀를 피합니다
  ([docs/DATABASE.md](./DATABASE.md) 4절).
- 다른 역할(회원/매니저/오너/플랫폼운영자)의 기존 접근이 이 변경으로 막히지 않는지 반드시 검토합니다 — 이 저장소는
  RLS 회귀 버그가 반복적으로 발생한 이력이 있습니다.

### 3-4. 기존 데이터 영향 확인
- 컬럼을 `NOT NULL`로 추가하면 기존 행의 기본값/백필 방법을 migration에 포함합니다.
- 컬럼/테이블 삭제는 사용 중인 `lib/*.ts` 코드가 없는지 먼저 확인합니다(`grep -rn "테이블명" lib/*.ts`) — 이 저장소에는
  스키마에만 존재하고 실제로는 안 쓰이는 테이블이 다수 있으므로([docs/DATABASE.md](./DATABASE.md) 1-8절 목록 참고)
  삭제해도 되는지 이 목록과 대조해 확인합니다. 그래도 삭제는 사용자 승인 후에만 진행합니다.

### 3-5. 코드 타입 반영
- `lib/*.ts`의 관련 타입(예: `type Foo = {...}`)과 select 컬럼 목록을 새 스키마에 맞게 갱신합니다.
- 이 타입을 쓰는 모든 `app/**/page.tsx`를 찾아 함께 갱신합니다.

### 3-6. 테스트
- 로컬(또는 스테이징) Supabase 프로젝트에 migration을 실제로 실행해보고, 관련 화면에서 CRUD를 수동으로 확인합니다.
- 회원/매니저 양쪽 권한으로 접근 테스트가 필요한 변경이면 두 역할 모두 확인합니다.

### 3-7. 문서 갱신
- [docs/DATABASE.md](./DATABASE.md)의 테이블 목록/SQL 파일 목록에 추가합니다.
- [docs/CHANGELOG.md](./CHANGELOG.md)에 기록합니다.
- README의 SQL 실행 순서 안내가 있다면(현재 일부만 명시됨) 새 파일의 의존 관계도 필요 시 덧붙입니다.
